# 提案：在搜尋結果中跨多段錄音問 AI（手動、附來源錄音）

## 市場參考
Otter「AI Chat」、Fireflies「AskFred」、Notta、Plaud 都能跨多場會議提問（例如「上個月客戶提過的報價是多少？」）並列出來源會議。RecorderApp 現有 #7／#59 只支援**單段**錄音問答；#32 跨錄音搜尋只做關鍵字比對。

## 不重複確認
#3–#82 與 main 都沒有跨錄音的 AI 問答。

## 行為
1. 搜尋畫面（#32）在有搜尋結果時顯示「問 AI（用這些結果）」按鈕；沒有結果時不顯示（使用者先用關鍵字／篩選縮小範圍）。
2. 來源錄音：先取逐字稿命中的錄音（依命中順序去重），再補搜尋結果中有逐字稿的錄音，最多 **6 段**；沒有可用逐字稿的錄音略過。
3. 每段只送預設逐字稿的**文字**，總長上限 48,000 字，平均分配，超過的段落截斷並在提示中標「（已截斷）」。
4. 使用者輸入問題後，**送出前確認**：顯示會送出的錄音數、約略字數、服務主機與摘要模型，寫明「1 次請求，可能產生 API 費用，不上傳音訊」。不自動重試。
5. 提示要求：只根據提供的逐字稿回答；每個論點附 `[R1]` 形式來源；找不到就回「這些錄音中沒有提到」。
6. 顯示回答，並把回答中**實際引用到**的 `[R#]` 列成來源 chip（錄音名稱），點了開啟該錄音播放頁。不存在的編號忽略，不捏造來源或時間。
7. 回答不儲存（關掉即消失），不改資料庫；可複製回答文字。

## 不做
- 不自動提問、不背景執行、不送到其他外部服務；不給片段時間（避免假時間）。
- 使用既有雲端設定（摘要模型與 API Key）；未設定時按鈕提示「尚未設定雲端摘要服務或 API Key」。

## 測試
純函式：來源挑選（去重、上限、略過無逐字稿）、字數分配與截斷、提示內容、`[R#]` 引用解析（忽略超出範圍、去重、保序）。
