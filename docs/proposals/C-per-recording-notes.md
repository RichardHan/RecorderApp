# 提案 C：每段錄音各自的會前／會中備註（取代 PR #2 的全域備註）

## 參考依據
- **Notion 官方文件**：會前可以把議程或背景寫在每則會議筆記的 Notes 下；產生摘要時，逐字稿和這些筆記都會被參考。https://www.notion.com/help/ai-meeting-notes （「Start AI Meeting Notes」段與 FAQ「Does the summary take my notes into account?」）
- **我們的做法**：把備註綁在每段錄音上。

## 使用者好處
不同會議有不同的議程，不必在每次會議之間手動改一個全域設定。

## 範圍（最小可行）
1. 錄音畫面加一個小的「備註」按鈕（高度不超過一行，觸控範圍至少 48dp），錄音前、錄音中都可以編輯。
   - 錄音前填的內容先暫存，錄音存檔時綁到這段錄音上。
2. 備註存在手機本機：`recordings/<id>/notes.json`（文字和更新時間），放在 TranscriptStore 的旁邊。
3. 播放頁可以看到並修改備註。修改後只影響之後產生的摘要。
4. 備註只在使用者已經開啟、並明確選定服務的雲端摘要裡才會被送出：
   - 即時重點：跟 PR #2 一樣，放進 prompt 裡並標註為「只供參考」。
   - 錄音後摘要：同樣標註為只供參考。
   - **只是在手機上寫了備註，不代表同意上傳**。沒有開啟雲端摘要時，備註永遠不會被送出。
5. 跟 PR #2 的關係：建議擇一。
   - 如果選 C，PR #2 可以改成「全域預設備註」，或直接關閉（由使用者決定）。

## 相依性
- 要動錄音的生命週期：錄音開始時清空暫存備註，存檔時綁到這段錄音。這部分要沿用 v1.7.14 的錄音隔離修正，**不能讓上一段的備註留到下一段**。
- 不依賴 PR #1。跟 PR #2 有功能重疊。

## 資料、隱私與費用
- 備註只存在手機上。
- 送出時，prompt 會多出備註的長度（上限 2000 字），會增加 token 用量。

## 邊界情況
- 取消錄音時，丟棄暫存備註。
- App 被系統關閉時，暫存備註要先寫到本機，下次開啟時詢問要不要套用到下一段錄音，或直接捨棄，不能自動帶入下一段錄音。
- 刪除錄音時，對應的備註一起刪除，跟現有的刪除逐字稿行為一致。

## 不在範圍內
- 不做日曆匯入議程。
- 不做多人共享備註。
- 不在錄音中提供有時間戳的筆記（現有的書籤已經可以加文字）。

## 驗收測試
- 錄完 A、再錄 B：B 的備註是空的，A 的備註仍然保存著。
- 雲端關閉時，任何流程都不會送出備註（用假的 HTTP 客戶端驗證）。
- 有備註時，摘要的 prompt 裡有標註「只供參考」的區塊；沒有備註時，prompt 跟原本完全一樣。

## 共通約束（所有提案都要遵守）
- **目前只是規格，還沒實作**。合併這份文件不代表功能已完成。
- 預設的重點整理 prompt 維持精簡；沒有重點時只回「目前無重點」，不強迫列出分類或待辦。
- 雲端功能預設關閉。API Key 一律由使用者明確選擇（轉錄 Key 與摘要 Key 分開）；任何把資料送到雲端的動作，都要先有使用者同意或手動確認。
- 時間戳只能來自真實的雲端分段（`SegmentResult.startMs/endMs`），不推測時間，也不編造說話者。
- 每段錄音的資料彼此隔離（參考 v1.7.14 的修正），不會互相影響。
- 原始逐字稿和摘要（`TranscriptRecord`/`SummaryRecord`）視為不可修改；任何修訂都另存成新的一筆，不覆蓋舊的。
- 基準分支：`feature/drive-auto-upload` @ c7f5e7f（v1.7.14）。
- 現有的 PR #1（逐字稿搜尋）、#2（全域會前備註）都還沒合併，也沒有被修改。
