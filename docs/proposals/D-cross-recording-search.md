# 提案 D：跨所有錄音搜尋逐字稿與重點（只在手機上）

## 參考依據
- **Notion 官方文件**：Meetings 分頁的清單可以篩選、排序、搜尋會議筆記（https://www.notion.com/help/ai-meeting-notes ，「AI Meeting Notes list view」段）。產品頁也說會議內容會成為可搜尋的團隊資料（https://www.notion.com/product/ai-meeting-notes ）。
- **我們的做法**：完全在手機上搜尋，不用雲端索引。

## 使用者好處
不記得是哪一場會議講的事，也能找到那一句，並直接跳到音檔的位置。

## 範圍（最小可行）
1. 錄音清單已經有搜尋（`feature/recordings/.../search`），在結果裡加一個「逐字稿內容」分區。
2. 在背景執行緒（IO）掃描每段錄音的 `TranscriptStore.transcripts()` 和 `summaries()`：
   - 依每段錄音預設選用的那份逐字稿（`PlaybackTranscripts.defaultSelection`）比對，避免同一段錄音重複出現。
   - 輸入時延遲約 300ms 才開始搜尋；新的輸入會取消上一次搜尋。
   - 快取每段錄音的逐字稿行，用檔案的更新時間判斷是否失效；**不會每打一個字就重新讀取所有檔案**。
3. 每筆結果顯示：錄音名稱、命中的那一行，以及時間（**只有在那份逐字稿真的有時間戳時才顯示**）。點擊會開啟播放頁，並跳到該位置。

## 相依性

- 如果 PR #1 沒有合併，D 要自己帶一份同樣的函式，兩邊會重複。

## 資料、隱私與費用
- 完全不呼叫任何 API，不需要網路。

## 邊界情況
- 已經移到垃圾桶的錄音不列入搜尋。
- JSON 損毀時略過該檔案，並記錄 log。
- 錄音和逐字稿很多時，限制最多回傳的筆數，並顯示「結果過多，請縮小關鍵字」。

## 不在範圍內
- 不做模糊、同音、語意搜尋。
- 不建全文索引資料庫（之後如果效能不夠再另外提案）。

## 驗收測試
- 搜尋函式：能比對多段錄音、會取消舊的搜尋、空白查詢不回傳結果。
- 沒有時間戳的逐字稿，結果不顯示時間。
- 用 500 段假逐字稿測試：不會卡住畫面（主執行緒不做 IO）。

## 相關程式路徑
- `feature/recordings/.../search/*`
- `cloudtranscribe/store/TranscriptStore.kt`
- `model/PlaybackTranscripts.kt`
- 播放頁的跳轉入口

## 共通約束（所有提案都要遵守）
- **目前只是規格，還沒實作**。合併這份文件不代表功能已完成。
- 預設的重點整理 prompt 維持精簡；沒有重點時只回「目前無重點」，不強迫列出分類或待辦。
- 雲端功能預設關閉。API Key 一律由使用者明確選擇（轉錄 Key 與摘要 Key 分開）；任何把資料送到雲端的動作，都要先有使用者同意或手動確認。
- 時間戳只能來自真實的雲端分段（`SegmentResult.startMs/endMs`），不推測時間，也不編造說話者。
- 每段錄音的資料彼此隔離（參考 v1.7.14 的修正），不會互相影響。
- 原始逐字稿和摘要（`TranscriptRecord`/`SummaryRecord`）視為不可修改；任何修訂都另存成新的一筆，不覆蓋舊的。
- 基準分支：`feature/drive-auto-upload` @ c7f5e7f（v1.7.14）。
- 現有的 PR #1（逐字稿搜尋）、#2（全域會前備註）都還沒合併，也沒有被修改。
